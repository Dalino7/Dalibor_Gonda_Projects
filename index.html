Problem

Performance data existed, but comparison did not.

Each match produced a GPS export that had to be inspected manually. Comparing players, halves and matches meant rebuilding the analysis in spreadsheets. The goal was a reusable workflow that required no technical work from the coach.

Product decision

Optimise the pilot for speed and zero licences.

Google Drive and Sheets provide a pragmatic ingestion and storage layer for the current volume. A static JavaScript application keeps deployment simple, removes licence requirements and gives the coach one stable link.

Delivered functionality

A product, not a static report

01

Player & team KPIs

Distance, top speed, sprints, calories, intensity and impacts switch dynamically between team averages and individual values.

02

Player rankings, first-vs-second-half decline, mechanical load, intensity and radar profiles for high-intensity work.

03

Cross-match trends

A dedicated view tracks the selected player and team over time and summarises all processed matches.

04

Bilingual delivery

Slovak and German interfaces share one calculation layer, while interface copy stays isolated in language files.

Engineering decisions

The hard part was making spreadsheet data dependable.

A

Multiple input formats

XLSX files are converted through the Drive API while CSV files are parsed directly. Both continue through the same validation path.

B

Type corruption

Values such as “8.01” were interpreted as dates. Explicit numeric typing, a unified date format and locale-aware decimal parsing made ingestion consistent.

C

Duplicate prevention

Processed files are registered by immutable file ID in a dedicated sheet so the same match cannot be ingested twice.

D

Stable deployment

The dashboard runs as a static application on Vercel. Updates ship without changing the link already shared with the coach.

  • Normalise by minutes playedShort appearances currently lower team averages.
  • Automate outlier detectionA 43.2 km/h reading exposes the need for domain thresholds.

Production evolution

How the architecture could scale beyond the pilot

Cloud Storage→Scheduled ingestion→BigQuery→SQL models & tests→Authenticated app

The existing system validates the user workflow. The next version would replace spreadsheet storage with a warehouse, introduce incremental loads, observability and formal data-quality tests while preserving the same zero-friction upload experience.

Research question

Can long-term satellite observations reveal drought stress in forest vegetation?

I used Python in Google Earth Engine to process Landsat 5–9 and Sentinel-2 imagery, calculate NDVI time series and anomalies, and identify drought-related vegetation stress. I then used R for statistical analysis and compared the satellite signal with climatic SPEI and phenological observations.

Methodological principle

No single dataset was treated as ground truth.

The result was tested across sensors and against independent observations. This separated persistent vegetation signals from sensor behaviour, seasonality and individual anomalous measurements.

Independent validation

The methodology held across sensors.

Landsat-derived vegetation dynamics were compared with Sentinel-2 and with observed spring leaf-out timing. The validation produced strong agreement while keeping the remaining bias visible.
